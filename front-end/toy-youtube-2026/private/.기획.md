# Zeno Tube 서비스 기획 초안

이 문서는 React 학습용 YouTube 서비스의 목적과 첫 버전 범위를 정리한 초안이다. 프로젝트 이름은 현재 폴더명을 따라 임시로 정했다. 멘토님이 확정한 요구사항이 아니라, 직접 생각하고 수정할 수 있는 출발점으로 사용한다.

| 문서 | 답하는 질문 |
| --- | --- |
| 선행지식.md | 구현하려면 무엇을 알아야 할까? |
| 기획.md | 누구를 위해 무엇을 만들고, 어디까지 완성할까? |
| 구조.md | 화면과 기능을 어떤 구조로 구현할까? |

## 1. 서비스 소개

**Zeno Tube는 영상을 탐색하고, 검색하고, 선택한 영상을 시청하는 웹 서비스다.**

사용자는 로그인 없이 홈의 영상 목록을 살펴보고, 관심 있는 주제를 검색한 다음, 상세 화면에서 영상을 시청할 수 있다.

이번 프로젝트에서는 이 탐색 흐름을 끝까지 연결하는 데 집중한다.

## 2. 프로젝트 목적

사용자에게 제공할 경험은 ‘관심 있는 영상을 찾아 시청하기’다.

개발자로서의 학습 목표는 다음과 같다.

- 화면을 역할별 컴포넌트로 나누고 그 이유를 설명한다.
- 사용자 행동에 따라 필요한 상태를 직접 설계한다.
- API 응답을 화면에 연결하고 요청 중·실패 상황도 처리한다.
- 화면 이동과 URL의 관계를 이해한다.
- 기획한 범위를 완성하고, 구현 과정에서 내린 선택을 설명한다.

## 3. 대상 사용자와 사용 상황

이 프로젝트에서 가정하는 사용자는 **보고 싶은 주제를 검색하거나 목록에서 영상을 골라 보고 싶은 사람**이다. 실제 사용자 조사 결과가 아닌 설계를 위한 가정이다.

대표 상황:

1. 딱히 정한 영상 없이 홈에 접속해 목록을 둘러본다.
2. ‘React 기초’처럼 관심 있는 주제를 검색한다.
3. 제목과 썸네일을 보고 영상을 선택한다.
4. 영상을 시청하고 다른 검색을 하거나 목록으로 돌아간다.

## 4. 첫 버전의 범위

첫 버전은 홈, 검색 결과, 영상 상세 세 화면으로 구성한다.

| 우선순위 | 기능 | 제공할 경험 |
| --- | --- | --- |
| 필수 | 홈 영상 목록 | 처음 접속했을 때 탐색할 영상이 보인다. |
| 필수 | 영상 검색 | 입력한 주제에 맞는 영상을 찾을 수 있다. |
| 필수 | 영상 상세 | 선택한 영상의 제목·채널·설명을 확인한다. |
| 필수 | 영상 재생 | 재생 가능한 영상을 임베드 플레이어로 시청한다. |
| 필수 | 페이지 이동 | 홈·검색·상세 사이를 이동하고 뒤로 갈 수 있다. |
| 필수 | 요청 상태 안내 | 기다리는 중인지, 실패했는지, 결과가 없는지 알 수 있다. |
| 필수 | 반응형 화면 | 모바일과 데스크톱에서 주요 기능을 사용할 수 있다. |
| 후속 | 결과 더 보기 | 검색 결과를 추가로 탐색한다. |
| 후속 | 최근 검색어 | 이전 검색어를 다시 사용한다. |
| 후속 | 브라우저 즐겨찾기 | 다시 보고 싶은 영상을 이 브라우저에 저장한다. |

후속 기능은 필수 기능을 완성한 뒤 선택한다. 로그인, 실제 계정의 구독·좋아요·댓글 작성, 영상 업로드, 개인화 추천은 첫 버전 범위에 포함하지 않는다.

## 5. 주요 사용자 시나리오

### 시나리오 A: 홈에서 영상 찾기

1. 사용자가 홈에 접속한다.
2. 목록을 가져오는 동안 로딩 안내가 보인다.
3. 영상의 썸네일·제목·채널명이 표시된다.
4. 사용자가 카드를 선택하면 해당 영상 상세로 이동한다.

### 시나리오 B: 주제로 검색하기

1. 검색창에 ‘React 기초’를 입력한다.
2. Enter 또는 검색 버튼으로 제출한다.
3. 제출한 검색어와 검색 결과를 확인한다.
4. 원하는 영상을 선택하거나 검색어를 바꿔 다시 검색한다.

### 시나리오 C: 영상 시청하기

1. 영상 상세 화면을 연다.
2. 제목·채널·설명을 확인하고 플레이어에서 재생한다.
3. 뒤로 가기로 이전 화면에 돌아가거나 로고로 홈에 이동한다.
4. 상세 주소를 직접 열거나 새로고침해도 해당 영상 화면이 열린다.

## 6. 화면별 요구사항

| 화면 | 반드시 보여줄 정보 | 가능한 행동 |
| --- | --- | --- |
| 공통 헤더 | 서비스 이름 또는 로고, 검색 폼 | 홈 이동, 검색 제출 |
| 홈 | 홈 목록의 성격을 나타내는 제목, 영상 카드 목록 | 영상 선택 |
| 검색 결과 | 제출한 검색어, 영상 카드 목록 또는 빈 결과 안내 | 영상 선택, 재검색 |
| 영상 상세 | 플레이어, 영상 제목, 채널명, 설명 | 재생, 다른 화면 이동 |
| 잘못된 경로 | 페이지를 찾을 수 없다는 안내 | 홈 이동 |

홈 목록은 초안 기준으로 인기 영상으로 정한다. 개인 맞춤 추천을 구현한 것으로 표현하지 않는다. 실제 데이터 연동 시 제공 가능한 조회 방식은 공식 문서로 확인한다.

## 7. 동작 규칙

### 검색

- 입력 중에는 요청하지 않고 제출할 때 검색한다.
- 제출한 값의 앞뒤 공백을 제거한다.
- 빈 검색어라면 요청하지 않고 입력 안내를 표시한다.
- 새 검색을 시작하면 이전 오류를 지우고 로딩 상태를 보여준다.
- 검색 결과 화면의 제목은 입력 중인 값이 아닌 제출한 검색어를 표시한다.
- 연속 검색에서는 마지막으로 제출한 검색어의 결과가 표시되어야 한다.

### 이동

- 로고를 선택하면 홈으로 이동한다.
- 영상 카드를 선택하면 그 영상의 상세 화면으로 이동한다.
- 검색어와 영상 ID는 URL로 해당 화면을 다시 열 수 있게 한다.
- 뒤로 가면 이전 검색어에 해당하는 결과 화면으로 돌아간다. 첫 버전에서는 다시 조회해도 괜찮다.
- 스크롤 위치 복원은 후속 개선으로 둔다.

### 실패와 빈 결과

- 요청 실패와 검색 결과 없음은 서로 다른 안내를 표시한다.
- 요청 실패 시 재시도를 제공한다.
- 상세 정보를 찾을 수 없으면 안내와 홈 이동을 제공한다.
- 영상 재생이 제한되는 경우를 고려하고, 필요하면 해당 영상의 YouTube 링크를 제공한다.

## 8. 디자인 방향

영상 썸네일과 제목을 쉽게 훑어볼 수 있는 배치를 우선한다. 초안은 밝은 배경, 읽기 쉬운 글자색, 하나의 강조색으로 시작한다.

- 영상 카드의 썸네일 비율과 간격을 일정하게 맞춘다.
- 긴 제목은 줄 수를 제한하고 상세 화면에서 전체 제목을 확인하게 한다.
- 검색창과 버튼은 쉽게 찾을 수 있는 위치에 둔다.
- 좁은 화면에서는 카드 열 수를 줄이고 플레이어를 화면 너비에 맞춘다.
- 키보드로 검색하고 링크와 버튼에 접근할 수 있게 한다.
- 입력창에는 용도를 알 수 있는 이름을 제공하고 포커스 위치가 보이게 한다.

색상, 로고, 카드 모양 등은 직접 정해도 된다. 첫 화면을 그린 뒤 반복해서 사용할 간격·글자 크기·색상을 간단하게 기록한다.

## 9. 데이터와 외부 의존성

초기 화면 작업에는 직접 작성한 목업 데이터를 사용한다. 실제 연동 단계에서는 YouTube Data API로 목록·검색·상세 정보를 가져오고, 임베드 플레이어로 영상을 재생하는 방향으로 진행한다.

구현 전에 확인할 사항:

- 각 화면에 필요한 데이터를 실제 요청으로 받을 수 있는가?
- API 요청 조건과 할당량 안에서 필수 기능이 동작하는가?
- 특정 영상이 조회되거나 재생되지 않을 때 어떤 안내를 할 것인가?

관련 영상 목록은 첫 버전 필수 기능이 아니다. 추후 추가한다면 목록을 고르는 기준과 사용 가능한 API를 먼저 확인한다.

## 10. 완료 기준

아래 항목을 직접 실행해 확인하면 첫 버전의 완료 여부를 판단할 수 있다.

- [ ] 홈에 접속하면 실제 영상 목록이 표시된다.
- [ ] 검색 버튼과 Enter 모두 검색을 실행한다.
- [ ] 공백만 제출하면 API 요청 없이 안내가 보인다.
- [ ] 검색 결과가 제출한 검색어와 일치한다.
- [ ] 영상 카드를 선택하면 올바른 상세 화면이 열린다.
- [ ] 상세 주소를 직접 열거나 새로고침해도 정보를 볼 수 있다.
- [ ] 재생 가능한 영상이 플레이어에서 재생된다.
- [ ] 로고로 홈 이동, 브라우저 뒤로 가기가 동작한다.
- [ ] 로딩·실패·빈 결과가 구분되어 표시된다.
- [ ] 실패한 요청을 재시도할 수 있다.
- [ ] 모바일 너비에서도 주요 내용이 화면 밖으로 넘치지 않는다.
- [ ] 키보드로 검색과 주요 화면 이동을 할 수 있다.

실제 API 성공뿐 아니라 목업이나 개발 환경을 활용해 오류와 빈 결과 상황도 확인한다.

## 12. 구현하면서 기록할 질문

멘토님께 결과를 설명할 때 다음 질문에 자신의 말로 답할 수 있도록 짧게 기록한다.

1. 첫 버전에서 이 기능들을 선택한 이유는 무엇인가?
2. 어떤 기준으로 컴포넌트를 나눴는가?
3. 검색 입력값과 제출한 검색어를 어떻게 구분했는가?
4. 상태를 해당 컴포넌트에 둔 이유는 무엇인가?
5. useEffect는 어디에 사용했고 왜 필요했는가?
6. API 실패와 늦게 도착한 응답을 어떻게 처리했는가?
7. 가장 어려웠던 문제와 해결 과정은 무엇인가?
8. 다음에 하나만 개선한다면 무엇을 선택하겠는가?
