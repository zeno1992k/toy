# YouTube 서비스 구조 설계 가이드

`선행지식.md`가 “어떤 기술을 배워야 하는가”라면, 이 문서는 “그 기술로 무엇을 어떻게 만들 것인가”를 정리한다.

아래 내용은 학습용 프로젝트의 설계 예시다. 멘토님이 세부 요구사항을 정해주지 않았다면 이 내용을 출발점으로 삼고, 직접 범위를 선택해보자. 실제 YouTube의 내부 구조를 설명하는 문서는 아니다.

## 1. ‘구조를 설계한다’는 뜻

처음에는 다음 다섯 가지를 정하면 된다.

| 구분 | 결정할 내용 | 예시 |
| --- | --- | --- |
| 기능 | 사용자가 무엇을 할 수 있는가? | 검색, 영상 선택, 재생 |
| 화면 | 그 기능을 어디에서 사용하는가? | 홈, 검색 결과, 영상 상세 |
| 컴포넌트 | 화면을 어떤 역할로 나눌 것인가? | 검색 폼, 영상 카드, 플레이어 |
| 데이터와 상태 | 무엇을 받아오고 무엇을 기억할 것인가? | 영상 목록, 입력값, 요청 상태 |
| 흐름 | 행동 이후 무엇이 바뀌는가? | 검색 제출 → 요청 → 결과 표시 |

폴더 이름은 이 결정을 코드에 옮기는 과정에서 정하면 된다. 먼저 사용자의 행동과 화면부터 생각하자.

## 2. 서비스의 목적을 한 문장으로 정하기

> 사용자가 영상을 찾아보고, 검색하고, 선택한 영상을 시청할 수 있는 서비스.

이 문장을 기준으로 첫 버전에 필요한 기능을 고른다.

### 첫 버전에 넣을 기능

- 홈에서 영상 목록 보기
- 검색어를 입력하고 검색 결과 보기
- 영상을 선택해 상세 화면으로 이동하기
- 상세 화면에서 영상 제목·채널·설명 보기
- 임베드 플레이어로 영상 재생하기
- 로딩·오류·검색 결과 없음 안내
- 좁은 화면에서도 사용할 수 있는 레이아웃

### 첫 버전이 동작한 뒤 추가할 기능

- 검색 결과 ‘더 보기’
- 최근 검색어 저장
- 이 브라우저의 즐겨찾기
- 설명 더 보기와 접기
- 채널 상세 화면

### 별도 범위로 생각할 기능

로그인, 실제 YouTube 계정의 구독·좋아요·댓글 작성, 영상 업로드, 개인화 추천은 인증이나 추가 설계가 필요한 기능이다. 처음부터 전부 과제 범위에 넣을 필요는 없다.

브라우저에 저장한 즐겨찾기는 실제 YouTube 계정의 좋아요와 다른 기능이다. 화면에서도 “즐겨찾기”처럼 구분해서 이름 붙인다.

## 3. 화면은 세 개로 시작하기

| 화면 | 목적 | 주요 내용 | 사용자 행동 |
| --- | --- | --- | --- |
| 홈 | 처음 볼 영상을 제공 | 헤더, 영상 목록 | 검색, 영상 선택 |
| 검색 결과 | 검색어에 맞는 영상을 제공 | 검색어, 결과 목록 | 재검색, 영상 선택 |
| 영상 상세 | 선택한 영상을 시청 | 플레이어, 제목, 채널, 설명 | 재생, 검색, 홈 이동 |

헤더는 모든 화면에 공통으로 둔다. 로고를 누르면 홈으로 이동하고 검색 폼은 어느 화면에서든 사용할 수 있게 한다.

사이드바는 필요하다면 나중에 추가한다. 메뉴를 먼저 만들기보다 각 메뉴가 연결될 실제 화면과 기능이 있는지 확인한다.

## 4. 화면 배치를 먼저 그려보기

종이에 사각형으로 그려도 충분하다. 색상과 세부 효과를 정하기 전에 정보의 위치를 정한다.

### 홈과 검색 결과

```text
┌───────────────────────────────────────────┐
│ 로고          [ 검색어 입력       ] [검색] │
├───────────────────────────────────────────┤
│ 화면 제목: 인기 영상 / ‘React’ 검색 결과   │
│                                           │
│ [썸네일]      [썸네일]      [썸네일]       │
│ 영상 제목     영상 제목     영상 제목      │
│ 채널명        채널명        채널명         │
│                                           │
│ [썸네일]      [썸네일]      [썸네일]       │
│ 영상 제목     영상 제목     영상 제목      │
│ 채널명        채널명        채널명         │
└───────────────────────────────────────────┘
```

검색 결과와 홈은 같은 영상 목록 컴포넌트를 재사용해도 된다. 첫 버전에서는 두 화면의 카드 배치를 동일하게 만들면 구현 범위가 작아진다.

### 영상 상세

```text
┌───────────────────────────────────────────┐
│ 로고          [ 검색어 입력       ] [검색] │
├───────────────────────────────────────────┤
│                                           │
│               영상 플레이어               │
│                                           │
├───────────────────────────────────────────┤
│ 영상 제목                                 │
│ 채널명                                    │
│ 영상 설명                                 │
└───────────────────────────────────────────┘
```

추가 영상 목록을 붙이고 싶다면 오른쪽이나 아래에 둘 수 있다. 어떤 근거로 고른 목록인지 먼저 정한다. 인기 영상을 표시한다면 ‘인기 영상’으로 이름 붙이고, 실제 추천 기능처럼 표현하지 않는다.

### 모바일에서 정할 것

- 검색창이 좁아지면 로고와 같은 줄에 둘지, 다음 줄로 내릴지
- 영상 카드가 한 열 또는 두 열 중 어느 배치가 읽기 좋은지
- 플레이어가 화면 너비를 넘지 않는지
- 긴 제목과 설명이 다른 요소를 밀어내지 않는지

## 5. 기능별 동작 규칙 정하기

“검색 기능이 있다”에서 한 단계 더 나아가, 동작을 구체적으로 적는다.

| 기능 | 시작 행동 | 처리 | 사용자에게 보이는 결과 |
| --- | --- | --- | --- |
| 홈 조회 | 홈 접속 | 영상 목록 요청 | 목록 또는 로딩·오류 안내 |
| 검색 | Enter 또는 검색 버튼 | 앞뒤 공백 제거 후 검색 | 제출한 검색어의 결과 |
| 빈 검색어 처리 | 공백만 입력 후 제출 | 요청하지 않음 | 입력 안내 |
| 영상 이동 | 카드 선택 | 영상 ID에 해당하는 화면 열기 | 상세 정보와 플레이어 |
| 홈 이동 | 로고 선택 | 홈 화면으로 이동 | 홈 목록 |
| 재시도 | 오류 화면의 재시도 선택 | 실패한 요청 다시 수행 | 로딩 후 결과 또는 오류 |

직접 결정할 질문:

- 입력할 때마다 검색할 것인가, 제출할 때 검색할 것인가?
- 새 검색 중에는 이전 결과를 유지할 것인가, 로딩 화면으로 바꿀 것인가?
- 상세에서 뒤로 가면 이전 검색어와 결과가 유지되어야 하는가?

첫 버전은 ‘제출할 때 검색’으로 시작하기 쉽다. 검색어 입력과 실제 요청 시점을 구분해서 이해할 수 있다.

## 6. 컴포넌트 구조

라우팅까지 도입한 버전의 예시다. 이름은 자유롭게 바꿔도 된다.

```text
App
├─ Header
│  └─ SearchForm
└─ 현재 URL에 맞는 페이지
   ├─ HomePage
   │  └─ VideoList
   │     └─ VideoCard × 여러 개
   ├─ SearchPage
   │  └─ VideoList
   │     └─ VideoCard × 여러 개
   └─ WatchPage
      ├─ VideoPlayer
      └─ VideoInfo
```

각 페이지에서 필요할 때 로딩·오류·빈 결과 안내를 표시한다. 반복이 생기면 `LoadingMessage`, `ErrorMessage`, `EmptyMessage`로 분리할 수 있다.

| 컴포넌트 | 맡은 역할 | 필요한 입력 예시 |
| --- | --- | --- |
| Header | 로고와 검색 영역 배치 | 검색 제출 처리 함수 |
| SearchForm | 입력과 제출 처리 | 제출 함수, 필요하면 초기 검색어 |
| VideoList | 배열을 카드 목록으로 표현 | 영상 배열 |
| VideoCard | 영상 한 개 표시와 상세 이동 | 영상 정보 |
| VideoPlayer | 선택한 영상의 플레이어 표시 | 영상 ID |
| VideoInfo | 제목·채널·설명 표시 | 영상 상세 정보 |
| 각 페이지 | 요청과 화면 상태 조합 | URL의 검색어 또는 영상 ID |

처음에는 페이지 안에 코드를 작성해도 된다. 같은 UI가 반복되거나 역할이 명확해질 때 컴포넌트로 분리한다.

## 7. 데이터와 상태를 구분하기

화면에 보이는 값이 모두 각각의 `useState`가 되어야 하는 것은 아니다.

| 종류 | 예시 | 보관 위치 예시 |
| --- | --- | --- |
| 입력 중인 값 | 검색창에 작성 중인 문자열 | SearchForm의 state |
| 화면을 식별하는 값 | 제출한 검색어, 시청할 영상 ID | 라우팅 도입 후 URL |
| API 결과 | 영상 목록, 영상 상세 | 요청을 담당하는 페이지의 state |
| 요청 진행 상태 | 로딩, 성공, 실패 | 요청을 담당하는 페이지의 state |
| 다른 값에서 계산하는 값 | 영상 개수, 결과가 비었는지 | 렌더링 중 계산 |
| 새로고침 후에도 남길 값 | 선택 기능인 최근 검색어 | localStorage 등 |

검색창에 `react`를 입력하고 제출한 뒤 `react hooks`로 고치고 있는 상황을 생각해보자. 입력 중인 값은 `react hooks`지만 현재 보이는 결과는 아직 `react`의 결과다. 그래서 ‘입력 중인 검색어’와 ‘제출한 검색어’를 구분한다.

### 상태 소유자를 정하는 기준

- 검색 입력값처럼 한 곳에서만 쓰면 해당 컴포넌트에서 관리한다.
- 여러 컴포넌트가 함께 쓰면 가장 가까운 공통 부모가 관리한다.
- URL로 식별하는 영상 ID를 별도의 선택 상태로 중복 관리하면 두 값이 어긋날 수 있다.
- 상태에서 계산할 수 있는 영상 개수는 별도로 저장하지 않는다.

### 라우팅 없이 시작하는 경우

연습용 첫 단계에서는 `App`이 영상 목록과 `selectedVideo`를 관리하고, 선택 여부에 따라 목록 또는 상세를 보여줄 수 있다. 이 방식은 페이지 URL 공유나 상세 화면 새로고침 처리가 제한된다.

URL을 도입하면 `WatchPage`는 URL의 영상 ID를 읽고 상세 데이터를 요청한다. 카드에서 전달받은 데이터가 없어도 상세 화면을 열 수 있도록 설계한다.

## 8. 행동부터 화면 변화까지 따라가기

### 검색 흐름

1. 사용자가 검색창에 입력한다.
2. SearchForm의 입력 상태가 바뀐다.
3. 사용자가 제출한다.
4. 공백을 제거하고 빈 값인지 검사한다.
5. 제출한 검색어로 검색 화면을 연다.
6. 해당 검색어의 영상 목록을 요청하고 로딩 상태를 표시한다.
7. 응답을 받으면 성공·빈 결과·오류 중 알맞은 화면을 표시한다.

라우팅을 도입했다면 제출 시 URL을 바꾸고 검색 페이지에서 요청하는 식으로 책임을 한 곳에 모을 수 있다. 제출 함수와 페이지 effect에서 같은 요청을 각각 실행하지 않도록 확인한다.

### 영상 선택 흐름

1. 사용자가 영상 카드를 선택한다.
2. 영상 ID를 포함한 상세 URL로 이동한다.
3. 상세 페이지가 해당 ID의 정보를 요청한다.
4. 플레이어와 영상 정보를 표시한다.
5. 조회할 수 없는 영상이면 안내 화면을 표시한다.

데이터 조회와 영상 재생은 역할이 다르다. 제목·설명 등은 데이터 API에서 받고, 재생은 임베드 플레이어를 사용하는 방향으로 설계한다.

## 9. 정상 화면 외에 필요한 화면

| 상황 | 화면에서 처리할 내용 |
| --- | --- |
| 첫 요청 중 | 로딩 안내 또는 스켈레톤 |
| 결과가 있음 | 영상 목록 |
| 검색 결과가 없음 | 다른 검색어 안내 |
| 요청 실패 | 오류 메시지와 재시도 |
| 상세 영상 조회 불가 | 영상 정보를 찾을 수 없다는 안내와 홈 이동 |
| 썸네일 표시 실패 | 대체 이미지 또는 빈 이미지 영역 |
| 영상 재생 제한 | 플레이어의 제한 안내, 필요하면 YouTube에서 열기 링크 |

‘결과 없음’은 요청에 성공했지만 데이터가 없는 상황이고, ‘오류’는 요청 자체에 실패한 상황이다. 두 경우를 구분한다.

빠르게 검색을 두 번 했을 때 늦게 도착한 첫 번째 응답이 두 번째 결과를 덮어쓸 수도 있다. API를 붙이는 단계에서는 요청 취소 또는 오래된 응답을 무시하는 처리도 확인한다.

## 10. API와 화면 사이의 경계

```text
페이지 → 서비스 함수 → YouTube API
페이지 ← 정리된 데이터 ← API 응답
   ↓
영상 목록 / 영상 정보 컴포넌트
```

페이지는 ‘검색 결과가 필요하다’를 결정하고, 서비스 함수는 ‘어떤 주소로 요청하고 응답을 어떻게 정리하는가’를 맡는다.

화면이 사용할 데이터 형태를 먼저 적어보자. 아래 이름은 프로젝트 내부에서 정한 예시이며 원본 API 필드 이름과 같을 필요는 없다.

```js
// 영상 목록용 데이터 예시
{
  id: "video-id",
  title: "영상 제목",
  channelTitle: "채널명",
  thumbnailUrl: "썸네일 주소"
}

// 상세 화면에는 필요에 따라 추가
// description, publishedAt 등
```

서비스 함수 이름의 예시:

- `getHomeVideos()`: 홈에 표시할 목록 가져오기
- `searchVideos(query)`: 검색어에 맞는 목록 가져오기
- `getVideo(videoId)`: 영상 상세 가져오기

먼저 이 형태의 목업 데이터를 사용하고, 나중에 서비스 함수 내부를 실제 API 요청으로 바꾸면 화면 개발을 이어가기 쉽다.

구현 시에는 공식 API 문서에서 제공 기능, 요청별 필드, 인증 조건, 할당량을 확인한다. 특히 ‘관련 영상’은 사용할 수 있는 전용 API가 있다고 가정해서 설계하지 말고, 구현 가능한 조회 방식과 목록의 의미를 먼저 확인한다.

## 11. URL 구조 예시

| URL | 의미 | 직접 접속했을 때 필요한 처리 |
| --- | --- | --- |
| `/` | 홈 | 홈 영상 목록 요청 |
| `/search?q=react` | react 검색 결과 | q를 읽어 검색 요청 |
| `/watch/VIDEO_ID` | 특정 영상 상세 | 영상 ID로 상세 요청 |
| 그 외 경로 | 존재하지 않는 화면 | 안내와 홈 링크 |

URL을 사용하면 새로고침, 링크 공유, 브라우저 뒤로 가기를 고려할 수 있다. 배포할 때는 상세 URL에 직접 접속해도 앱이 열리도록 호스팅 설정을 확인해야 한다.

## 13. 직접 구현하는 순서와 완료 기준

| 순서 | 할 일 | 이 단계가 끝났다는 기준 |
| --- | --- | --- |
| 1 | 필요한 화면을 종이에 그리기 | 각 화면의 정보와 이동 경로를 설명할 수 있음 |
| 2 | 목업 데이터로 홈 만들기 | 영상 카드 여러 개와 검색창이 보임 |
| 3 | 카드 클릭과 상세 만들기 | 선택한 영상의 제목과 설명이 바뀜 |
| 4 | 목업 검색 동작 만들기 | 제출 후 필터링 결과와 빈 결과가 구분됨 |
| 5 | URL과 페이지 연결하기 | 상세 직접 접속과 뒤로 가기가 의도대로 동작함 |
| 6 | 실제 API 연결하기 | 실제 목록·검색·상세가 동작하고 오류도 표시됨 |
| 7 | 플레이어 연결하기 | 재생 가능한 영상이 상세 화면에서 재생됨 |
| 8 | 모바일과 키보드 사용 확인 | 화면이 넘치지 않고 입력·이동이 가능함 |

각 단계를 끝낼 때 ‘화면에 보인다’뿐 아니라 ‘사용자 행동 이후 기대한 상태가 된다’를 확인한다. 클릭 가능한 카드는 링크나 버튼 같은 의미에 맞는 요소로 만들고, 검색창에는 접근 가능한 이름을 제공한다.
