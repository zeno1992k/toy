# 06. 커밋 메시지 규칙

## 1. 왜 규칙을 정하는가?

커밋 기록만 읽어도 무엇을 왜 바꿨는지 알 수 있게 하기 위해서다. 모든 회사에 공통인 단일 규칙은 없다. 아래는 Conventional Commits 형식을 참고한 **이 토이 프로젝트의 권장 규칙**이다.

좋은 기록의 기준은 멋있는 표현보다 실제 변경과의 일치, 명확한 범위, 일관성이다.

## 2. 기본 형식

```text
타입(선택적인 범위): 변경 내용 요약

필요하면 변경 이유와 동작 설명

필요하면 관련 이슈 또는 호환성 변경
```

```text
feat(search): 검색어 제출 시 영상 목록 조회

입력 중인 검색어와 제출한 검색어를 구분한다.
빈 검색어는 요청하지 않고 안내를 표시한다.
```

- 타입: 변경 목적.
- 범위(scope): search, layout, api처럼 바뀐 영역. 생략 가능.
- 요약: 무엇을 바꿨는지 한 줄.
- 본문: 요약으로 부족할 때 이유·동작·제약 설명.
- 푸터: 실제 연결할 이슈나 호환성 변경이 있을 때 사용.

형식과 feat·fix·호환성 변경 의미는 [Conventional Commits 공식 규격](https://www.conventionalcommits.org/en/v1.0.0/)을 참고한다. 아래의 다른 타입과 문체는 프로젝트 관례다.

## 3. 자주 쓰는 타입

| 타입 | 선택 기준 | 이 프로젝트 예시 |
| --- | --- | --- |
| `feat` | 사용자 기능·화면 추가 | 영상 검색 구현 |
| `fix` | 잘못된 동작 수정 | 빈 검색어 요청 방지 |
| `docs` | 문서만 변경 | 학습 노트 추가 |
| `style` | 의미·동작을 유지한 코드 형식 변경 | 들여쓰기·공백 정리 |
| `refactor` | 기능을 유지한 구조 개선 | API 요청을 서비스 함수로 분리 |
| `perf` | 성능 개선 | 중복 요청 제거 |
| `test` | 테스트 추가·수정 | 검색 제출 테스트 |
| `build` | 빌드·의존성 관련 변경 | Vite 설정 변경 |
| `ci` | 자동 실행 파이프라인 변경 | CI 빌드 검사 추가 |
| `chore` | 위에 속하지 않는 유지보수 | 개발 도구 설정 정리 |
| `revert` | 이전 변경 되돌리기 | 잘못된 요청 방식 되돌리기 |

모든 타입을 처음부터 쓸 필요는 없다. 추가 타입의 세부 의미는 팀에 따라 다르다.

### 3-1. 영어 뜻과 커밋에서 사용하는 이유

모든 타입이 약어는 아니다. feat·docs·perf는 줄임말이고 ci는 머리글자 약어다. 나머지는 영어 단어나 개발 용어다. 아래는 단어 뜻과 사용 관례를 연결한 설명이며 역사적 명명 유래를 단정하는 설명은 아니다.

#### feat → feature: 기능·특징

- feature는 제품이 제공하는 기능이나 특징을 뜻한다.
- 커밋에서는 feature를 줄인 feat를 사용한다.
- 새로운 화면이나 사용자가 할 수 있는 일을 추가하므로 ‘기능 추가’ 타입이다.
- 사전의 독립된 단어 feat는 ‘위업·공적’이라는 뜻도 있지만 여기서는 feature의 줄임말이다.
- 예: `feat(search): 영상 검색 기능 추가`

#### fix: 고치다·수리하다

- 약어가 아니라 ‘고치다’라는 영어 단어다.
- 프로그램의 잘못된 동작을 고치는 것을 bug fix라고 부른다.
- 그래서 버그 수정에 사용한다. 파일을 수정했다고 모두 fix는 아니다.
- 예: `fix(search): 공백 검색어로 API를 호출하는 문제 수정`

#### docs → documentation: 문서·문서화 자료

- docs는 documents 또는 documentation을 가리키는 흔한 줄임말이다.
- README·설명서·학습 노트 등 문서를 바꿀 때 사용한다.
- 예: `docs: 커밋 타입의 영어 뜻과 사용 이유 추가`

#### style: 스타일·표현 방식

- 약어가 아닌 영어 단어다.
- 이 프로젝트에서는 화면 디자인이 아니라 code style, 즉 코드 작성 형식을 뜻한다.
- 들여쓰기·공백·포맷팅처럼 코드 의미를 유지하는 변경에 사용한다.
- CSS 디자인 변경은 기능 추가·오류 수정 등 목적에 따라 판단한다.
- 예: `style: JSX 들여쓰기 통일`

#### refactor: 코드를 리팩터링하다

- 외부 동작을 유지하면서 내부 구조를 개선한다는 소프트웨어 용어다. refactoring은 그 작업을 가리킨다.
- 함수 분리나 중복 정리로 읽기·수정·재사용을 쉽게 할 때 사용한다.
- 코드를 많이 바꿨다는 이유만으로 쓰지는 않는다.
- 예: `refactor(api): 영상 조회 코드를 서비스 함수로 분리`

#### perf → performance: 성능

- 실행 속도·메모리·응답성 등 프로그램의 처리 효율을 뜻한다.
- 성능 개선을 주목적으로 한 변경에 사용한다.
- 코드가 짧아졌다고 반드시 빨라지는 것은 아니므로 개선 근거를 확인한다.
- 예: `perf(search): 동일 검색어의 중복 요청 감소`

#### test: 시험하다·검사하다 / 테스트

- 약어가 아닌 영어 단어다.
- 프로그램 동작을 확인하는 테스트 코드를 추가·수정할 때 사용한다.
- 수동으로 앱을 실행해봤다는 이유로 기능 변경을 test라고 하지는 않는다.
- 예: `test(search): 빈 검색어 제출 테스트 추가`

#### build: 만들다·조립하다 / 빌드

- 소프트웨어에서는 소스 코드를 실행·배포 가능한 결과물로 만드는 과정을 뜻한다.
- 그 과정의 설정이나 의존성 변경에 사용한다.
- npm run build를 실행했다는 사실만으로 build 커밋을 만드는 것은 아니다. 기록할 변경이 있어야 한다.
- 예: `build: Vite 빌드 출력 경로 변경`

#### ci → Continuous Integration: 지속적 통합

- 여러 변경을 자주 합치고 자동 빌드·테스트 등으로 통합 상태를 확인하는 개발 방식이다.
- GitHub Actions 등의 CI 설정 파일·스크립트를 바꿀 때 사용한다.
- CI는 특정 서비스 이름이 아니다.
- 예: `ci: pull request에서 lint와 build 검사 실행`

#### chore: 정기적으로 해야 하는 일·잡무

- 약어가 아닌 영어 단어다. 집안일을 뜻하는 household chores에서도 사용한다.
- 프로젝트에도 기능 개발 외에 도구 설정·불필요한 파일 정리 같은 관리 작업이 필요하다.
- 그런 유지 작업을 묶는 관례라서 chore를 환경 설정·유지보수에 사용한다.
- 가치 없는 일이라는 뜻은 아니다. 애매한 변경을 전부 넣는 만능 타입도 아니다.
- build·ci·docs처럼 더 구체적인 목적이 있으면 그 타입을 먼저 고려한다.
- 예: `chore: 에디터 공통 설정 추가`

#### revert: 이전 상태로 되돌리다

- 약어가 아닌 영어 단어다.
- 이전 커밋의 변경을 취소하는 변경을 기록할 때 사용한다.
- 새 방식으로 오류를 고치는 fix와 달리 특정 변경을 되돌리는 것이 목적이다.
- 본문에 실제 되돌리는 커밋과 이유를 적으면 추적하기 쉽다.
- 제목에 revert라고 적는 것만으로 Git이 자동으로 되돌리지는 않는다.
- 예: `revert: 검색 자동 제출 변경 되돌리기`

### 3-2. 같은 ‘설정 변경’도 목적에 따라 구분

| 변경 내용 | 이 프로젝트에서 선택할 타입 |
| --- | --- |
| 에디터 공통 설정 | `chore` |
| Vite 빌드 옵션·의존성 | `build` |
| GitHub Actions 자동 검사 | `ci` |
| 설정 방법 설명 문서 | `docs` |
| 잘못된 설정으로 발생한 실제 오류 해결 | 주된 목적에 따라 `fix` |

의존성 업데이트를 build로 분류하는 팀도, chore로 분류하는 팀도 있다. 모든 팀의 규칙을 외우기보다 이 프로젝트의 기준을 일관되게 적용한다.


## 4. CSS를 바꾸면 style인가?

이 문서의 규칙에서는 아니다. **파일 확장자가 아니라 변경 목적**으로 판단한다.

```text
feat(layout): 헤더와 사이드바 Grid 배치 추가
fix(layout): 좁은 화면에서 콘텐츠가 넘치는 문제 수정
refactor(css): 공통 색상을 CSS 변수로 통합
style: CSS 들여쓰기와 공백 정리
```

새 화면·배치면 feat, 기존 화면의 오류면 fix, 동작을 유지한 정리면 refactor를 검토한다.

## 5. 요약 문장 작성 기준

이 프로젝트에서는 다음 문체를 권장한다.

- 타입은 소문자 영어로 통일한다.
- 콜론 다음에 공백 한 칸을 둔다.
- 설명은 한국어로 작성해도 된다.
- 한 줄에 읽기 쉽게 쓰고, 자세한 내용은 본문에 적는다.
- 요약 끝의 마침표는 생략한다.
- “추가”, “수정”, “분리”, “제거”, “연결”처럼 구체적인 변경을 적는다.
- 확인하지 않은 기능 완성이나 테스트 통과를 적지 않는다.

제목 50자, 본문 72자 같은 길이 기준은 흔한 권고일 수 있으나 모든 프로젝트의 필수 규칙은 아니다.

| 피할 표현 | 개선 예시 |
| --- | --- |
| `수정` | `fix(search): 검색 결과가 이전 요청으로 덮이는 문제 수정` |
| `오늘 작업` | `feat(layout): 기본 페이지 영역 배치` |
| `완료` | `docs: CSS 학습 예제 정리` |
| `feat: 유튜브 완성` | `feat: 헤더·사이드바·본문 뼈대 구성` |

## 6. 한 커밋의 범위

되도록 **하나의 설명 가능한 목적**으로 묶는다. 반드시 한 파일일 필요는 없다.

- 검색 기능에 필요한 컴포넌트·API 함수 변경은 함께 묶을 수 있다.
- 무관한 문서 수정과 버그 수정은 분리할 수 있다.
- 커밋을 잘게 나누기 위해 일부러 동작하지 않는 상태를 만들 필요는 없다.
- 이미 공유한 기록은 메시지를 예쁘게 만들겠다고 함부로 재작성하지 않는다.

## 7. 지금까지의 작업에 적용한다면

아래는 변경이 실제로 포함된 경우에만 쓰는 예시다.

### 초기 작업을 한 커밋으로 묶을 때

```text
feat: 유튜브 서비스 기본 화면 구조 및 레이아웃 구성

- Vite 기반 React 개발 환경 구성
- Header, Sidebar, Content 컴포넌트 작성
- 공통 CSS 초기화 및 Grid 레이아웃 적용
- 학습 내용과 작업 흐름 문서 정리
```

API·검색·재생이 아직 없으면 구현했다고 적지 않는다. 문서를 커밋에 넣지 않았다면 문서 항목도 뺀다.

### 목적별로 나눌 때

```text
chore: Vite 기반 React 개발 환경 구성
feat(layout): 헤더·사이드바·본문 Grid 배치
docs: CSS와 접근성 학습 노트 추가
```

### 이번 두 문서만 커밋할 때

```text
docs: 커밋 메시지와 코드 이름 규칙 정리
```

## 8. 커밋 전 확인 순서

프로젝트 루트에서 직접 실행하는 예시다. 아래 문서 경로는 이 저장소 기준이다.

```bash
git status
git diff
git add "insight/06_커밋메시지_규칙.md" "insight/07_변수명_규칙.md"
git diff --staged
git commit -m "docs: 커밋 메시지와 코드 이름 규칙 정리"
```

- `git status`: 변경·추적 상태 확인.
- `git diff`: 추적된 파일의 아직 stage하지 않은 변경. 신규 미추적 파일 내용은 나오지 않을 수 있다.
- `git add`: 이번 커밋에 넣을 변경 선택.
- `git diff --staged`: 실제 커밋할 내용 확인.
- `git commit`: 로컬 기록 생성. GitHub 업로드와는 별개다.

다른 변경이 이미 stage되어 있으면 해당 변경도 커밋에 포함된다. 반드시 staged 전체 내용을 확인한다.

## 9. 호환성을 깨는 변경

라이브러리 사용자나 API 소비자가 기존 방식대로 사용할 수 없게 되는 변경은 `!` 또는 `BREAKING CHANGE:`로 표시할 수 있다.

```text
refactor(api)!: 영상 목록 응답을 객체 형식으로 변경

BREAKING CHANGE: 배열 대신 items 속성을 가진 객체를 반환한다.
```

단순 파일명 변경이나 작은 내부 정리를 모두 호환성 변경이라고 부를 필요는 없다. 실제 소비자가 의존하는 계약이 있는지 판단한다.

## 10. 최종 체크

- [ ] staged 내용과 메시지가 맞는가?
- [ ] 타입이 파일 종류가 아닌 변경 목적을 나타내는가?
- [ ] 아직 구현하지 않은 기능을 적지 않았는가?
- [ ] 개인 파일·키·불필요한 산출물이 포함되지 않았는가?
- [ ] 본문이 필요한 경우 이유와 결과를 설명했는가?

이 문서 작성은 규칙 안내일 뿐이며 Git 커밋·푸시는 별도 작업이다.
